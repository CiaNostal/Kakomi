# 開発セッションログ: インタラクティブなテキスト配置とUndo/Redoの実装（2026-08-26）

このドキュメントは、Kakomiに対して行った1回の開発セッションの経緯・検討過程・実装内容を記録したものです。`spec.md`が「現在のアプリの仕様」を記述するのに対し、本ドキュメントは「なぜその設計に至ったか」という過程を記録するのが目的です。

## 1. きっかけ

もともとの相談内容は次の2点だった。

- 写真に文字列を追加・配置する部分が不便
  - インタラクティブな操作ができない（UIを操作する場所と、それが反映・表示される箇所が完全に分断されている）
  - 文字列が2個しか追加できない
- このアプリはGitHub Pages上で動くブラウザ完結型のクライアントサイドアプリであり、現状はJavaScript / HTML / CSSのみを使用している

この制約の中でインタラクティブなテキスト配置・生成が実現できるか、というのが出発点だった。

## 2. 検討過程

### 2.1 アーキテクチャ調査

既存コードを調査した結果、以下が判明した。

- `stateManager.js`が持つ単一の`editState`を唯一の真実とし、UI操作→`updateState`→再描画、という一方向フローで動くimmediate-mode描画（毎回全部描き直す）方式
- テキストは`freeText`/`freeText2`という2つの決め打ちプロパティとして、`stateManager.js`・`textRenderer.js`・`uiController.js`・`index.html`の4箇所にコピペで実装されていた（配列ではないため3個目を足すには同じコピペをもう1箇所増やす必要がある構造）
- リポジトリには`Kakomi_refactoring.md`というFabric.jsを用いた全面リライト計画書が存在したが、未実装だった

GitHub Pages上の静的クライアントアプリという制約は、追加ライブラリをCDN経由で読み込む（`piexif.js`と同様）か、完全にVanillaのままでも問題にならないことを確認。技術的に「Vanilla JSのままでは無理」という項目はなく、Fabric.jsのような外部ライブラリへの全面リライトは不要と判断した。

### 2.2 アプリ全体の「イケてない」点の洗い出し

テキストの問題は氷山の一角で、「UIとプレビューの分断」という同じ構造的問題が以下にも及んでいることを確認した。

- 写真の配置（`photoPosX/Y`）: スライダーのみ、ドラッグ不可
- 背景ぼかしの位置（`imageBlurBackgroundParams.offsetX/YPercent`）: `-500%〜500%`という扱いにくいレンジのスライダーのみ
- 構図調整（`cropSettings`）: 内部実装はあるがUIが一切なく、常にデフォルト値固定（死んでいる機能）
- `resetState()`と状態変更リスナーの仕組みがコードには存在するが配線されておらず未使用
- Undo/Redo、プリセット保存、カラー履歴、出力前の拡大確認、出力フォーマット選択肢、モバイル最適化、バッチ処理、レイヤー管理がいずれも未実装

### 2.3 インタラクティブ操作と数値精度の両立

ドラッグ操作は直感的だが精密な数値指定ができない、という懸念に対しては、以下の方針で合意した。

- ドラッグと数値入力は排他ではなく共存させる
- 数値入力は「ドラッグ可能な数値入力」（Figma/After Effects風のスクラブ入力）に置き換える
- 矢印キーでの1px単位nudgeを併用する
- 将来的にスナップ/ガイドも追加する

### 2.4 共通ドラッグ基盤の設計

「テキストのドラッグ配置」を単体機能として作るのではなく、Kakomi全体の操作性を底上げする共通基盤として設計した。要点は以下。

- **状態通知のバッチ化**: `notifyStateChange()`を`queueMicrotask`でバッチ化し、`updateState(updates, {silent:true})`で派生データ（レイアウト計算結果）の書き戻しが無限ループにならないようにする
- **当たり判定の登録機構**（`interactionRegistry.js`）: immediate-mode描画を変えずに、「描画するたびに帳簿を作り直す」設計で当たり判定を持たせる
- **オブジェクトごとのアダプタ**（`adapters/*.js`）: テキスト・写真・背景で単位系が異なる（写真短辺基準の% / 可動範囲に対する0-1の割合 など）ため、共通コントローラに変換ロジックを持ち込まず、種別ごとの小さなアダプタに閉じ込める
- **選択状態は`editState`と分離**（`selectionStore.js`）: 一時的なUI状態であり、書き出しファイルやUndo履歴に含めるべきではないため
- **スナップ/ガイドの受け口**: ドラッグのpointermoveハンドラ内、差分パッチ確定前に差し込むだけで済むように設計しておく

## 3. 実装内容

実装は以下の順序で段階的に進めた。

1. 状態通知のバッチ化（`stateManager.js`）
2. `interactionRegistry` / `canvasInteraction`の骨組み
3. `freeText`/`freeText2` → `customTexts[]`への配列化とテキスト用アダプタ、ドラッグ・選択の実装
4. スクラブ入力コンポーネント（`js/ui/scrubInput.js`）
5. 矢印キーnudge
6. 写真配置・背景オフセットへのアダプタ追加（`photoAdapter.js`, `backgroundAdapter.js`）
7. スナップ/ガイド（`snapEngine.js`, `guideStore.js`）
8. ドキュメント整合性の修正（`spec.md`・`README.md`更新、`Kakomi_refactoring.md`削除、`resetState()`削除）
9. Undo/Redo（`js/history/historyManager.js`）

最終的なファイル構成は`spec.md`の4章・5.12〜5.18節、および`README.md`のプロジェクト構成を参照。

### 3.1 見つかった不具合と修正

**テキストドラッグの移動量が大きすぎる不具合**: `textAdapter.js`の座標変換で、プレビューcanvas上のドラッグ量（px）を、既に「プレビュー描画時に縮小された後の短辺px」であるはずの`photoShortSidePx`に対して、さらに`scale`で除算する誤った二重変換をしていた。プレビューの縮小率次第でドラッグ量が数倍に増幅され、画面端で吹き飛ぶ現象として現れた。ドラッグとnudgeの両方でこの変換を修正し、以後Playwrightでの検証で1:1の移動量になることを確認した。

### 3.2 テスト方法

このWSL2環境には素のLinux版Node.jsが入っていないため、動作確認にはWindows側のnode.exe（`/mnt/c/Program Files/nodejs/node.exe`）経由でPlaywright + Chromiumをインストールして使用した。WSL側のファイルへは`\\wsl.localhost\Ubuntu-24.04\...`というUNCパスでアクセスする。検証セッションごとに`npm install playwright` → `playwright install chromium`を行い、確認後は`node_modules`・`AppData\Local\ms-playwright`を削除してクリーンアップした（ユーザー承認済み）。

アプリ自体は`python3 -m http.server`でローカルサーバーを立てて確認した（`file://`では ES Modules のCORS制限により動作しないため）。

各実装フェーズで、実際にブラウザ（Chromium）上でドラッグ・スクラブ・キーボードnudge・Undo/Redoなどの操作をシミュレートし、コンソールエラーの有無と期待される状態変化を確認しながら進めた。

## 4. 現状のステータス

- テキスト・写真・背景いずれもプレビュー上でドラッグ配置でき、スナップ/ガイド、矢印キーnudge、スクラブ数値入力が一貫した設計の上で動作する
- Undo/Redo（Ctrl+Z / Ctrl+Shift+Z、ヘッダーボタン）が編集設定を対象に機能する
- ドキュメント（`spec.md`, `README.md`）は実装と整合が取れている
