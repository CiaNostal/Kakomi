## 2. プリセット保存・カラー履歴

### 設計判断
- 保存対象のキー一覧を`stateManager.js`に`EDITABLE_SETTINGS_KEYS`として切り出し、既存のUndo/Redo（`historyManager.js`の`TRACKED_KEYS`）と新設のプリセット保存の両方がこれを共有する形にリファクタリングした。「編集設定として保存・復元すべき範囲」の定義が2箇所に重複するのを避けるため。
- カラー履歴は「全カラーピッカー共通」の単一履歴とし、`<input type="color">`の直後にスウォッチ行を動的挿入する方式（`ui/colorSwatches.js`）にした。`.form-row-simple`はflexコンテナのため、素朴にinput直後へ挿入すると同じ行に横並びになってしまう不具合に途中で気づき、行コンテナ自体の直後（兄弟要素）に挿入するよう修正した。
- 自由テキストの色ピッカーのように毎回作り直されるDOM（`customTextSettingsPanel`）に対しては、スウォッチ行の再描画対象を`registry`で管理し、DOMから外れた行を`isConnected`チェックで間引くことでメモリリークを防いだ。

## 3. 構図調整（クロップのズーム・パン）の数値UI化

### 見つけたバグと再設計
UIを生やす前提として`layoutCalculator.js`のクロップ計算を読んだところ、実装上のバグを発見した。旧実装は「アスペクト比に基づく基準窓をoffsetX/Yで配置してから、その中心を軸にズームで縮小する」という順序だったため、`aspectRatio: 'original'`（元画像と同じ比率、パン可動範囲が最初から0）の状態でズームインしても、パンが一切効かないという問題があった。ズームによって新たに生まれるはずの可動範囲が、offsetXの適用タイミングの都合で失われていたため。

UIから触れるようになれば即座に露見する問題だったため、計算順序を「ズーム後のサイズを先に決め、そこから生まれる可動範囲でoffsetX/Yによるパンを行う」方式に書き直した。これにより「ズームした分だけパンできる」という直感的な挙動になった。

### UI
出力アスペクト比と同じ「プリセットselect＋幅/高さ自由入力＋⇄反転ボタン」パターンを流用し、「レイアウト設定」タブの先頭に「構図調整（トリミング）」フィールドセットとして追加した。

## 4. テキストの拡大・回転ハンドル

### 設計方針
- `customTexts[]`の各レイヤーに`rotation`（度数）フィールドを追加。
- 選択中のテキストにのみ、右下角に拡大ハンドル（四角）、上端中央から少し離れた位置に回転ハンドル（丸、接続線付き）を表示する。
- 当たり判定は`interactionRegistry`の既存のAABB方式を拡張し、`rotation`を持つエントリは「クリック座標をボックス中心を軸に逆回転させてからAABB判定する」方式にした（回転前のローカル座標系を常に保持する設計）。回転・逆回転の計算は`utils/geometry.js`の`rotatePoint()`に共通化した。
- 拡大は「中心からハンドルまでの距離の比」を開始時サイズに掛けるだけの単純な実装にした。回転角によらず「ハンドルを中心から遠ざける/近づける」という直感的な動作になる。
- ハンドルの画面座標は`interaction/textHandleStore.js`（`guideStore.js`と同じ「描画側が書き、操作側が読む」一時状態パターン）に保持し、`canvasInteraction.js`のpointerdownが通常の当たり判定より先にハンドルとの距離判定を行う。

## 5. 撮影日・Exif情報のUI刷新（ユーザーからの追加相談）

一通り実装を終えて次の相談事項を尋ねたところ、「文字入力のUIが自由テキストに比べて弱い」という指摘があり、以下を実施した。

### 5.1 撮影日
- フォーマットが5種類のプリセットselectのみだった点を、出力アスペクト比と同じ「プリセット＋自由入力」のハイブリッドに変更（`getFormattedDate()`は元々`YYYY`/`YY`/`MM`/`DD`のトークン置換方式だったため、ロジック変更は不要だった）。
- 撮影日ブロックはそもそも`interactionRegistry`に登録されておらず（`id`を持たないタスクとして描画されていた）、ドラッグで動かせなかった。`textRenderer.js`のdrawTextで固定id（`'text-date'`）を振るよう変更し、ドラッグ対象にした。

### 5.2 Exif情報
- 従来は「チェックボックスで項目を選ぶ→`uiController.js`内にハードコードされた固定順（`displayOrder`）で並べたテキストを自動生成→そのテキストを手動編集用のテキストエリアに表示」という設計だった。しかしチェックボックスを1つ変えるたびに手動編集内容が丸ごと上書きされる壊れた導線だった。
- ユーザーと相談の上、「チェックボックス＋手動編集」を廃止し、「利用可能な項目をクリックで追加」→「使用する項目をドラッグで並び替え」という2段構成のUIに置き換えた（並び替えは`items`配列の並び順をそのまま表示順として使うよう`updateExifCustomText()`を修正）。生成結果は読み取り専用のプレビュー欄で確認する（自動生成のみ、手動上書きは廃止）。
- 並び替えの実装は外部ライブラリを使わず、`canvasInteraction.js`と同じ「素のPointer Eventsを直書き」の流儀にした。HTML5 Drag and Drop APIはタッチ対応が弱く、本アプリの「タッチデバイス動作未検証」という課題と相性が悪いため意図的に避けた。ドラッグ中はDOM上の行要素を直接並べ替えるだけで状態には書き込まず、`pointerup`時に最終順序をまとめて一度だけコミットする2段階方式にした（後述の教訓を参照）。
- 追加のExifタグとして露出補正（`ExposureBiasValue`）を追加した（他の候補タグはユーザーの選択で見送り）。
- 撮影日と同様、Exifブロックにも固定id（`'text-exif'`）を振ってドラッグ対応にした。

### 5.3 実装中に得た教訓（ドラッグ中の状態書き込みタイミング）
Exif項目の並び替えUIを実装する際、「ドラッグ中に`updateState()`のたびにリストDOM全体を再構築する」設計にすると、ドラッグ中の行要素自体が作り直されてポインタ操作が中断する、という問題に気づいた（`pointerdown`で確立したイベントリスナー・ポインタ捕捉の対象DOM要素が消えてしまうため）。これは、拡大・回転ハンドルの実装で確立していた設計（Canvas描画とDOM要素という違いはあるが）と同じ教訓であり、「ドラッグ中は表示のみをその場で操作し、状態への書き込みはドロップ時に1回だけ行う」という原則として再確認した。

## 6. ユーザー報告による3件の不具合修正

一通りの実装を終えてユーザーに確認してもらったところ、以下3件の報告があった。

### 6.1 オフセット表示の桁あふれ
`textAdapter.js`・`backgroundAdapter.js`の`computeChanges()`（ドラッグ・矢印キーnudge共通）が、`(dxPx / photoShortSidePx) * 100`という割り算結果をそのまま状態に加算し続けていたため、循環小数（例: `-11.640211640211641`）がそのまま蓄積し、表示スパンが桁あふれを起こしていた。0.1%単位に丸めるよう修正し、表示側にも`.toFixed(1)`を防御的に追加した。ユーザーから「他にも同じバグがあるのでは」と指摘され、実際に`backgroundAdapter.js`（拡大ぼかし背景のドラッグ）にも全く同じパターンの不具合が見つかった。

この修正の過程で、拡大・回転ハンドルの動作確認中に別の潜在バグを発見した。`selectionStore`の選択状態変更（`setSelectedId()`）は`editState`の変更ではないため、`stateManager.js`の通常の状態変更リスナー（`requestRedraw`等）を経由せず、再描画をトリガーしない。ドラッグを伴わない純粋なクリック選択（`pointerdown`直後に一度も`pointermove`が発火しないケース）では、選択ハイライトやハンドルが次の何らかの状態変更まで表示されないという抜け穴があった。実マウス操作では通常わずかな移動が伴うため気づきにくいが、Playwrightの`page.mouse.click()`（ゼロ移動の正確なクリック）で偶然発見した。`main.js`で`selectionStore.onSelectionChange(() => requestRedraw())`を明示的に登録し、選択変更でも必ず再描画されるようにして解消した。

### 6.2 Exif情報プレビューの文字化け
最初、ユーザーからの報告だけでは原因を特定できず（添付された画像が写真そのものでテキスト部分が写っていなかったため）、実際の写真ファイル（`DSCF0404.JPG`）のパスを教えてもらい、Pythonで直接EXIF APP1セグメントをバイナリ解析した。

結果、原因はUTF-8のエンコーディング問題ではなく、**EXIF ASCII型フィールドの固定長パディング用NULバイト**だった。`Make`タグは`"CampSnap"`の後ろにNULバイトが22個、`Model`タグは`"CS-V201"`の後ろに24個続いていた（Exif規格上、ASCII型フィールドは固定長でNUL終端・パディングされる仕様通り）。piexif.jsはこれをそのまま文字列化して返すため、末尾のNUL文字群が制御文字として可視化され「特殊文字が混ざったような文字化け」に見えていた。

最初の修正提案（UTF-8をLatin-1として誤読した場合の復元、`escape()`+`decodeURIComponent()`）はこの原因には対処できておらず、ユーザーからの再指摘で判明した。`exifHandler.js`の`decodeExifString()`に、最初のNUL文字以降を切り捨てる処理を追加して解決した（UTF-8誤読の復元処理は保険として残した）。

**教訓**: 文字化けの原因は複数パターンありうる（エンコーディング不一致、固定長フィールドのパディング等）。ユーザー報告だけで推測して対策するのではなく、可能な場合は実データを直接バイナリレベルで確認すべきだった。

なお、この文字化けドキュメント作業の過程で、コメント中に「NUL文字」を説明しようとして誤って生のNULバイト（`\x00`）をソースファイル（`exifHandler.js`、`spec.md`）に直接埋め込んでしまうミスがあった。`git diff`が該当ファイルを「バイナリファイル」として扱ってしまう症状で発覚し、Pythonで生バイトを直接置換して`\u0000`という正しいエスケープシーケンスに修正した。テキストとして「NUL文字」を扱う際は、実際の制御文字ではなくエスケープ表記で記述するよう注意する。

### 6.3 ハンドルの復活
前回、撮影日・Exifブロックには「位置移動のみ、ハンドルなし」と決めていたが、ユーザーの意向が変わり「自由テキストと全く同じ拡大・回転ハンドルが欲しい」となった。

- `textSettings.date`/`textSettings.exif`に`rotation: 0`を追加。
- `textAdapter.js`の`commitResize`/`commitRotate`を、`commit()`と同様に`FIXED_TEXT_IDS`（`'text-date'` → `date`、`'text-exif'` → `exif`）を見て書き戻し先を振り分ける`applyChanges()`ヘルパー経由にした。
- サイズのクランプ範囲は対象ごとに異なるスライダー範囲（自由テキストは`textFreeSize`で最大50%、撮影日/Exifは`textDateSize`/`textExifSize`で最大10%）を`getSizeConfigKey(id)`で選択するようにした（当初、全て`textFreeSize`でクランプしていたら、日付Exifのサイズスライダーの表示上限を超える値になってしまう不具合になるところだった）。
- `canvasRenderer.js`側で以前追加していた「`'text-date'`/`'text-exif'`は`drawTextHandles()`を呼ばない」という除外ガードを削除した。

## 7. テスト方法

前回セッションと同じ方法（WSL2にはLinux版Node.jsがないため、Windows側の`node.exe`経由でPlaywright + Chromiumをインストールして使用）。検証後は`node_modules`・`AppData\Local\ms-playwright`を削除してクリーンアップした。

本セッションでは、実際のEXIFデータをテストするために以下の工夫をした。

- ブラウザに実在の画像を読み込ませた後、`page.evaluate()`内で`import('/js/stateManager.js')`のように対象モジュールを動的importし、`updateState()`や各種ストアの内部関数を直接呼び出してテスト用の状態（合成したExifデータ等）を注入する手法を多用した。DOM操作だけでは再現しにくい状態（実カメラのEXIF、特定の内部状態）を直接検証できて有効だった。
- 文字化け調査では、実際にユーザーから教えてもらった写真ファイルパスを使い、Pythonで直接JPEGのAPP1セグメントをバイナリパースしてタグの生バイト列を確認した。ブラウザ上の見た目の描写だけでは分からない原因（NULパディング vs エンコーディング）を切り分けるのに必須の手順だった。
